# 下单意图日志迁移与恢复边界

适用版本：未发布的 `3.111.0-rc6`。未访问生产数据库，未执行生产迁移。

## 新增契约

- `execution_intents` 以完整 owner scope 摘要和 ClientOrderID 唯一定位；scope 含账户非敏感完整摘要、交易所、市场、交易对、Bot，不使用 API Key 前缀。记录原始经济请求、开平仓分类、最后一次提交尝试价格与次数、已观察回执、UNKNOWN 及 CAS 修订号。
- 提交前同步落库，明确拒单重试的每次尝试也在调用前保存。交易所接单与数据库写入不是分布式事务：接单后写失败保留 UNKNOWN；数据库提交回执不确定时停止后续写入，不能用旧修订号盲重试或覆盖。
- SQLite 写入连接使用 `PRAGMA synchronous=FULL`；已测试设置生效、文件关闭重开、并发 CAS 及故障注入，但没有物理断电演练。MySQL 部署应核对 InnoDB/binlog 刷盘、复制及备份策略；SQL 已提供，未在 MySQL 实例验收。
- 这是一份订单意图/观察状态日志，不是完整逐笔成交/费用财务日志。终态（包括 FILLED）不等于策略、资本和账本已结清，不能据此跳过恢复。

## 显式迁移

1. 取得目标实例变更批准，停止相关交易写入并备份数据库。不要将真实连接串、密钥或凭据写入文档/命令日志。
2. 在隔离测试数据库审查、执行并验证相应 up SQL：
   - SQLite：`storage/migrations/2026092402_execution_intents_sqlite.up.sql`
   - MySQL：`storage/migrations/2026092402_execution_intents_mysql.up.sql`
3. 核对唯一键、分页索引、时间列及读写权限。迁移幂等，不改写既有 orders/trades 数据。正常应用启动不会调用迁移方法，缺表报错不等于“第一次启动”。
4. 先核对旧数据的账户/Bot 归属、历史成交与资金预留，再升级运行。**本版尚无完整旧数据导入和自动经济恢复流程；不能迁完表就把旧账户当全新账户运行。**

## 当前恢复行为

- 绑定发生在 SPM Initialize/策略 StartAll 之前。分页读取所有意图，不只读取 NEW/PARTIALLY_FILLED；空白、损坏、归属矛盾、数据库不可用都保守阻断。
- 对已恢复的非明确拒绝意图，保留请求/CID/订单号/策略归属并要求经济核账。恢复后的未知平仓同样阻止同方向盲目补平。
- 只有日志无待核账记录、没有相关旧 orders 历史，且交易所核实该交易对无持仓/挂单的全新运行时，才移除本流程自身的启动阻断；其他暂停来源不受影响。现货已有基础资产余额不能推定为本 Bot 可用库存，保持阻断。
- 有旧历史、现存仓位/订单或未结算意图时，本版**不会自动恢复开仓**。普通手动恢复不会移除独立恢复来源；目前没有“清空日志即可恢复”的支持操作。接下来必须实现完整策略 lot、累计成交、费用及资本检查点/重放。
- 路由和实时回报只接受本 Bot 已登记或已验证恢复的意图；不会从同交易对其他账户/Bot 的历史订单猜测归属。

## 回滚与未覆盖项

- 两份 down SQL 会删除意图日志。仅在一次性测试库演练；生产需另行批准、停止写入并先导出。通常代码回滚应保留本表，不能删表或改 Bot/凭据身份绕过未知状态。
- 凭据轮换/账户迁移、旧日志导入、跨进程单活与全账户协调尚待完整设计验收，完整账户摘要本身不解决这些问题。
- R04 的账户级手工/退出等遗留直接调用尚未全部统一到共享执行器，不在本次日志覆盖承诺内。R05 逐笔财务日志、R09 自动经济恢复、R12 持仓/在途硬额度仍必须继续完成。
