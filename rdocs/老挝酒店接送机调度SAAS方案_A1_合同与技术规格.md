## 第一部分：试点合同/服务条款模板（可直接复制改名）

> 文档名称建议：`《机场接送调度系统试点合作协议》`

### 1. 合作双方

- **甲方**：酒店/民宿经营主体（公司名称/店名/地址/联系人/电话）
- **乙方**：系统服务提供方（公司/个人名称/地址/联系人/电话）

### 2. 定义

- **系统/服务**：乙方提供的“接送机调度与沟通留痕”软件服务（Web/移动端/PWA），用于收集接送信息、派单、记录状态、生成报表与导出数据。
- **接送任务**：一次接机或送机的调度记录（含客人信息、航班信息、司机信息、状态与日志）。
- **试点期**：双方约定的试运行周期（建议 14 天），用于验证价值与流程适配。
- **按单计费**：以“完成的接送任务单量（或计费单量规则）”为计费基数。

### 3. 服务范围（A1）

乙方在试点期提供：
- 客人端登记链接/二维码、表单收集
- 酒店端任务看板、派单、异常按钮、复制消息模板
- 司机端任务列表与 4 步状态按钮（确认/到达/接到/完成）
- 日报/周报（如有）、导出对账（CSV/Excel）
- 基础培训与试点复盘报告（建议包含异常率、等待时间、单量统计）

明确不包含（A1 范围外）：
- 乙方不提供车辆与司机，不承诺运力与准时率
- 不承诺接入携程/Agoda/Booking 等 OTA 或酒店 PMS
- 不提供线下接待/举牌/保险等运营服务

### 4. 双方责任与配合义务

#### 4.1 甲方责任

- 指定系统对接人（建议：前台主管/前厅经理）
- 负责向客人发送登记链接/二维码（通过 OTA 站内消息、微信、短信等）
- 提供并维护司机/车队信息（司机名单、联系方式、车牌等）
- 确保司机与前台按 SOP 使用系统并及时更新状态
- 对线下服务质量、司机行为、交通安全、保险、运营合规等承担责任

#### 4.2 乙方责任

- 提供可用的系统服务、账号与基础培训
- 保障数据基本安全与访问权限控制（见“数据与隐私”）
- 提供试点期内的基础技术支持（响应时间见 SLA）
- 在试点结束后提供复盘报告（如双方约定）

### 5. SLA（服务可用性与支持）

建议条款（可按你的实际能力调整）：
- **服务可用性目标**：试点期内月度可用性不低于 99%（不含计划维护与第三方不可抗力）
- **支持时段**：工作日 09:00–18:00（万象时间）在线支持；紧急问题可升级（见下）
- **响应时间**：
  - P0（系统不可用/无法派单）：2 小时内响应
  - P1（核心功能异常但有替代方案）：8 小时内响应
  - P2（优化需求/非阻断问题）：3 个工作日内响应

### 6. 数据、隐私与信息安全

#### 6.1 数据最小化原则

系统仅收集完成接送所必需信息，例如：
- 客人姓名、联系方式（微信/电话/邮箱可选）、航班号、到达日期、人数/行李、备注（可选）

#### 6.2 数据归属

- 接送任务数据与报表数据原则上归甲方所有；乙方仅为提供服务而处理数据。

#### 6.3 数据保留与删除

建议条款：
- 任务完成后数据默认保留 **180 天**（可协商）
- 甲方可随时导出；终止合作后，乙方在 **30 天**内提供一次完整导出并按约定删除/匿名化

#### 6.4 访问控制

- 账号按角色分权（经理/前台/司机）
- 司机仅可访问分配给自己的任务信息
- 所有关键操作留痕（审计日志/时间线）

#### 6.5 禁止行为

甲方不得：
- 将乙方系统用于非法用途或违反当地法律/平台规则的用途
- 试图绕过权限、批量爬取、攻击系统等

### 7. 计费与结算（按单）

#### 7.1 计费口径（建议写清楚）

按单计费的“单”建议定义为：
- **计费单** = 状态达到 `COMPLETED` 的接送任务（或 `PICKED_UP` 视为完成，二选一写死）

可选：对 `CANCELED` 是否计费、`NO-SHOW` 是否计费写清楚，例如：
- 客人取消/航班取消：不计费
- 客人 NO-SHOW 且司机已到达并等待 ≥ X 分钟：计费/半价计费（可选）

#### 7.2 价格与套餐

在合同中写一张表（示例）：

| 版本 | 单价 | 包含内容 |
|------|------|----------|
| 基础版 | ¥6 / $0.8 每单 | 表单、派单、状态留痕、复制模板 |
| 标准版 | ¥12 / $1.6 每单 | 基础版 + 异常闭环 + 日报 + 对账导出 |
| 加强版 | ¥20 / $2.7 每单 | 标准版 + 周报 + 司机表现 + 自定义字段 |

可选：最低消费（如按 50 单/月计费）写清楚。

#### 7.3 结算周期

建议：
- 每月对账一次（按系统导出的计费单量）
- 甲方在对账确认后 **7 天**内付款

### 8. 试点条款（14 天）

建议写明：
- 试点起止日期
- 试点范围（例如仅接机，不含送机；或仅白天时段）
- 试点对接人、培训安排
- 试点结束交付物：复盘报告 + 导出数据
- 试点转正式：默认续用/另签正式合同/按月自动续费（按你偏好）

### 9. 免责与责任限制（非常关键）

建议写清边界（A1 纯软件）：
- 乙方不对因司机迟到、交通事故、客人迟到/失联、通讯不可用、航班变更等导致的损失承担责任
- 因系统故障导致的直接损失，乙方责任上限通常不超过**当期已收服务费**（可按试点费用或月度费用封顶）

### 10. 知识产权与保密

- 系统软件、代码、商标等归乙方
- 甲方业务数据归甲方
- 双方对对方的商业信息保密（至少包含价格、流程、客户信息）

### 11. 终止与退出

建议条款：
- 任一方提前 X 天书面通知可终止（试点期建议 3 天或即时）
- 终止后乙方提供数据导出并删除/匿名化
- 未结算费用按对账结果支付

### 12. 争议解决与适用法律

此处需结合你的主体所在地与签约方式选择（模板示例）：
- 适用法律：老挝法律 / 中国法律（择一）
- 争议解决：协商 → 仲裁/法院（地点：万象/你所在地）

## 第二部分：A1 技术规格（产品规格 + 数据模型 + API 草图）

> 目标：让你能快速做出可用 MVP，并支持多酒店（多租户）扩展。

### 1. 非功能性要求（MVP 必备）

- **多租户隔离**：酒店之间数据严格隔离
- **弱网可用**：司机端优先 PWA（离线缓存、弱网重试）
- **审计留痕**：核心操作必须写不可变事件日志
- **导出能力**：酒店端能导出对账与任务明细（减少“数据被锁死”顾虑）
- **简单上手**：前台 20 分钟培训可用；司机 10 分钟可用

#### 1.1 弱网/断网设计清单（A1 必做）

万象实际环境常见问题是 **网络断续与弱网**，尤其是司机侧移动网络。A1 的目标是：**允许延迟同步，但不允许业务丢单/重复派单/状态乱跳**。

**前台端（酒店）**
- **写操作幂等**：派单/取消/异常/编辑任务等写操作建议支持 `Idempotency-Key`，服务端对同 key 的重复请求返回同结果，防止弱网重试造成重复派单/重复事件。
- **操作反馈清晰**：区分“已提交/待确认/失败可重试”，避免前台连点。
- **显示同步状态**：任务详情展示“司机最后上报时间/最后同步时间”，减少误判。

**司机端（重点）**
- **离线队列**：`accept/arrive/pickup/complete` 在本地落盘队列（IndexedDB/SQLite/LocalStorage 任选），网络恢复自动补传。
- **最终一致**：服务端以事件时间线合并，允许客户端延迟提交（但要校验状态迁移合法）。
- **轻量资源**：尽量不用大图与重依赖，确保弱网可打开。

**客人端**
- **页面极简**：首屏快、可重复提交（同一表单重复提交要能识别并避免创建多条任务）。
- **无网兜底**：取车码 + 等待点说明要能在“预抵达消息”里提前告知，避免落地没网导致完全失联。

**服务端**
- **状态机在后端**：所有状态变更由服务端校验合法性（避免前端弱网导致乱序写入）。
- **事件不可变**：`task_events` 追加写入；同类重复事件（例如 arrive 重复上报）要做去重/折叠策略。

#### 1.2 弱网验收用例（交付时可直接勾选）

- 前台在弱网下连续点击“派单”不会产生重复派单（看 `task_events` 只有一次 ASSIGNED）。
- 司机离线状态下依次点击“到达→接到→完成”，网络恢复后能自动补传并最终变为 `COMPLETED`。
- 司机重复点击同一状态按钮不会让任务跳回/跳过状态（状态迁移受控）。
- 客人重复提交表单（同姓名+同航班+同日期）不会产生两条任务（或能提示“已提交/请勿重复提交”）。
- 断网时前台能看到明确提示，知道哪些操作不会立即生效。

### 2. 角色与权限（RBAC 最小模型）

- `MANAGER`：查看报表、导出、司机管理、酒店设置
- `FRONTDESK`：创建/编辑任务、派单、处理异常、复制消息模板
- `DRIVER`：仅查看分配给自己的任务，更新 4 步状态

建议权限原则：
- 司机不可见其他司机任务
- 前台可见全部任务，但不可删除审计日志

### 3. 核心实体（数据模型草图）

> 字段命名可按你的语言栈调整；这里偏“业务字段优先”。

#### 3.1 `hotels`

- `id`
- `name`
- `city`（Vientiane/LuangPrabang）
- `timezone`（默认 Asia/Vientiane）
- `pickup_instructions_text`（等待点说明）
- `pickup_instructions_image_url`（可选）
- `created_at`, `updated_at`

#### 3.2 `users`

- `id`
- `hotel_id`
- `role`（MANAGER/FRONTDESK/DRIVER）
- `name`
- `phone`（可选）
- `wechat_id`（可选）
- `password_hash` / `oauth_provider`（择一）
- `status`（active/disabled）
- `created_at`, `updated_at`

#### 3.3 `drivers`（可选：也可复用 users 表，role=DRIVER）

- `id`
- `hotel_id`
- `name`
- `phone`
- `car_plate`
- `car_desc`（颜色/车型）
- `active`

#### 3.4 `transfer_tasks`

核心字段（A1）：
- `id`
- `hotel_id`
- `type`（pickup/dropoff；A1 可只做 pickup）
- `source`（guest_form/manual）
- `status`（见下）

客人信息：
- `guest_name_cn`
- `guest_name_en`（拼音/英文）
- `guest_wechat`
- `guest_phone`（可选）
- `guest_email`（可选）

行程信息：
- `flight_no`
- `arrival_date`（日期）
- `arrival_estimated_time`（可选；A1 可先不拆分时分秒）
- `passenger_count`
- `luggage_count`（可选）
- `need_chinese_sign`（bool，可选）
- `has_internet`（bool，可选）
- `notes`（可选）

派单信息：
- `assigned_driver_id`（或 assigned_user_id）
- `pickup_code`（4 位码）

统计字段（可选）：
- `driver_arrived_at`
- `picked_up_at`
- `completed_at`
- `canceled_reason`（可选）

#### 3.5 `task_events`（审计日志/时间线，强烈建议不可变）

- `id`
- `hotel_id`
- `task_id`
- `actor_user_id`（谁操作的）
- `actor_role`
- `event_type`（TASK_CREATED / ASSIGNED / ACCEPTED / ARRIVED / PICKED_UP / COMPLETED / EXCEPTION_RAISED / CANCELED / FIELD_UPDATED）
- `event_data`（JSON：旧值/新值/原因/备注/定位等）
- `created_at`

### 4. 状态机（A1 建议）

- `NEW`：客人提交
- `ASSIGNED`：已派单（司机未确认）
- `ACCEPTED`：司机确认接单
- `ARRIVED`：司机到达机场
- `PICKED_UP`：接到客人（可要求输入取车码）
- `COMPLETED`：送达完成
- `EXCEPTION`：异常处理中（可与主状态并行，或作为状态）
- `CANCELED`：取消

建议规则（写在服务端，避免“前端乱跳状态”）：
- 仅允许按顺序推进（允许 CANCELED 从任意非终态进入）
- EXCEPTION 允许从任意非终态触发，并记录原因，但不一定阻断主状态推进

### 5. API 草图（REST，MVP 足够）

> 建议所有接口都带租户上下文（JWT 中含 hotel_id），服务端再做二次校验。

#### 5.1 认证

- `POST /api/auth/login`（前台/经理登录）
- `POST /api/auth/driver-login`（司机邀请码/手机号登录，按你策略）
- `POST /api/auth/refresh`（可选）

#### 5.2 客人表单（无需登录）

- `GET /public/h/:hotelSlug/pickup-form`（表单页面数据：酒店名、等待点说明）
- `POST /public/h/:hotelSlug/transfer-tasks`
  - 入参：表单字段
  - 出参：`task_id`、`pickup_code`、等待点说明、下一步指引

#### 5.3 酒店端任务

- `GET /api/transfer-tasks?date=YYYY-MM-DD&status=...`
- `GET /api/transfer-tasks/:id`
- `POST /api/transfer-tasks/:id/assign`（派单）
  - 入参：driver_id
- `POST /api/transfer-tasks/:id/cancel`
  - 入参：reason
- `POST /api/transfer-tasks/:id/exception`
  - 入参：exception_type + notes
- `PATCH /api/transfer-tasks/:id`
  - 仅允许编辑有限字段（航班号、人数、备注等），并写入 `task_events`

#### 5.4 司机端任务

- `GET /api/driver/tasks?date=YYYY-MM-DD`
- `POST /api/driver/tasks/:id/accept`
- `POST /api/driver/tasks/:id/arrive`
- `POST /api/driver/tasks/:id/pickup`
  - 入参：pickup_code（可选必填）
- `POST /api/driver/tasks/:id/complete`

#### 5.5 报表与导出

- `GET /api/reports/daily?date=YYYY-MM-DD`
- `GET /api/reports/weekly?week=YYYY-WW`（可选）
- `GET /api/exports/tasks?from=...&to=...`（返回 CSV/Excel 下载）

### 6. 消息模板（A1：先做“复制按钮”）

建议后端返回可复制文本，前端提供“一键复制”：

- 给客人模板（派单后）：
  - 司机姓名、车牌、等待点、取车码、找不到时的处理方式
- 给司机模板（派单后）：
  - 客人姓名、航班、预计时间、人数、取车码、联系渠道、等待点

后续再做：
- 自动发送（WhatsApp/SMS/企业微信）
- 多语言模板与变量插值

### 7. 最小前端页面结构（便于你快速搭 UI）

- `PublicPickupFormPage`（客人表单）
- `PublicPickupSubmittedPage`（提交成功页：取车码 + 等待点 + 提示）
- `HotelDashboardPage`（看板：按状态列）
- `TaskDetailDrawer`（任务详情 + 时间线 + 按钮）
- `DriverTasksPage`（司机任务列表）
- `DriverTaskDetailPage`（大按钮 4 步）
- `ReportsPage`（日报/导出）
- `SettingsPage`（酒店信息、等待点说明、司机管理）

### 8. 指标埋点（为“试点复盘报告”服务）

建议在服务端即可计算：
- `assigned_at - created_at`（派单时延）
- `accepted_at - assigned_at`（司机响应）
- `arrived_at - accepted_at`（到达耗时）
- `picked_up_at - arrived_at`（等待耗时）
- `completed_at - picked_up_at`（送达耗时）
- 异常率（异常事件 / 总单）
- 取消率（取消单 / 总单）

### 9. 开发落地建议（你一年 4–8 次往返的节奏）

建议你优先做：
- 多租户 + RBAC + 状态机 + 审计日志 + 导出

暂缓做：
- 航班自动跟踪（需要第三方数据源与稳定性）
- OTA/PMS 官方对接（周期不可控）
- 自动派单/路线优化（先用“手动派单 + 留痕”跑通价值）
