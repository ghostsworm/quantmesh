# 网格盈亏 vs 交易所盈亏：为什么差这么多？

> **创建日期**: 2025-03-03  
> **目的**: 解释 QuantMesh 网格策略计算的盈亏与交易所返回的已实现盈亏之间可能出现的巨大差异（包括性质相反的情况）

---

## 现象：我们算赚 155，交易所显示亏 4.5

这不是 bug，而是**两种完全不同的计算口径**导致的必然结果。

---

## 两种计算方式

### 1. 网格盈亏（QuantMesh 计算）

```
网格 PnL = Σ (卖出价 - 该槽位平均买入价) × 数量
```

- **按槽位配对**：每个网格槽位独立核算
- 槽位 A：60,000 买入 → 65,000 成交 → +50 USDT（正常挂单成交）
- 槽位 B：70,000 买入 → 65,000 成交 → -50 USDT（**仅当止损/风控全平仓时**，被迫在市价 65,000 附近成交；正常网格不会挂低于买入价的卖单）
- **合计**：0（或正或负，取决于每格买卖价差）

### 2. 交易所盈亏（交易所 API 返回）

```
交易所 PnL = Σ (卖出价 - 持仓加权平均成本) × 卖出数量
```

- **按持仓整体**：不区分槽位，所有持仓混在一起算一个「成本价」
- 持仓均价 = (60k×0.01 + 70k×0.01) / 0.02 = **65,000**
- 在 65,000 卖出 0.01 → 交易所 realized_pnl = 0

---

## 为什么会出现「我们赚、交易所亏」？

### 典型场景：高位加仓后下跌

> **重要说明**：正常网格下，每个槽位的卖出价 = 买入价 + 利润间距，**不会**挂低于买入价的卖单。  
> 下表「卖出价 65,000」指的是**实际成交价**，仅在以下情况发生：**止损/风控触发全平仓**时，系统用市价或略低于市价快速平仓，此时市价若为 65,000，则 70,000 买入的槽位会被迫在 65,000 附近成交（亏损）。  
> 若未触发全平，70,000 槽位的卖单会挂在 70,000+利润间距，只有价格涨上去才会成交。

| 槽位 | 买入价 | 数量 | 实际成交价* | 网格 PnL | 交易所 PnL |
|------|--------|------|-------------|----------|------------|
| 1 | 60,000 | 0.01 | 65,000 | +50 | 取决于持仓均价 |
| 2 | 62,000 | 0.01 | 65,000 | +30 | 取决于持仓均价 |
| 3 | 70,000 | 0.02 | 65,000 | -100 | 取决于持仓均价 |

\* 槽位 3 在 65,000 成交 = 止损/风控全平仓导致，非正常网格挂单

**持仓均价** = (60×0.01 + 62×0.01 + 70×0.02) / 0.04 = **65.5k**

- 槽位 1 卖出：网格 +50，交易所 (65-65.5)×0.01 = **-5**
- 槽位 2 卖出：网格 +30，交易所 (65-65.5)×0.01 = **-5**
- 槽位 3 卖出：网格 -100，交易所 (65-65.5)×0.02 = **-10**

**网格合计**：+50 + 30 - 100 = **-20**  
**交易所合计**：-5 - 5 - 10 = **-20**

这个例子两边一致。但当**卖出顺序**和**持仓结构**不同时：

- 若你先卖出的是低价买入的槽位，网格会先体现盈利
- 交易所的持仓均价会随每次卖出而变化，可能一直高于你的卖出价
- 结果：**网格显示正，交易所显示负**

### 核心原因

1. **持仓加权均价** vs **槽位买入价**：交易所不关心你的槽位，只关心「整体成本」
2. **卖出顺序**：每次卖出后持仓均价会变，影响下一笔的 realized_pnl
3. **高位加仓**：若在上涨中买了很多，持仓均价被拉高，后续在较低价卖出时，交易所会记亏损

---

## 哪个数字更「真实」？

| 用途 | 建议参考 |
|------|----------|
| **策略表现**（网格是否在赚钱） | 网格盈亏 |
| **账户结算、税务、提现** | 交易所盈亏 |
| **与交易所对账** | 以交易所为准 |

交易所的 realized_pnl 是**实际结算依据**，资金划转、强平、爆仓都按这个来。网格盈亏更适合评估策略逻辑是否正确。

---

## 如何排查差异？

### 1. 使用诊断 API

```
GET /api/statistics/pnl/diagnosis?exchange=binance&symbol=BTCUSDT
```

返回示例：

```json
{
  "pnl_comparison": {
    "grid_pnl": 155,
    "exchange_pnl": -4.5,
    "discrepancy": 159.5,
    "discrepancy_explanation": "盈虧性質相反：網格按槽位買賣配對計算...",
    "orders_with_realized_pnl": 45,
    "sell_orders_missing_pnl": 2
  }
}
```

- `sell_orders_missing_pnl` > 0：有卖单未拿到交易所的 realized_pnl，可能漏记
- `discrepancy_explanation`：系统给出的差异原因说明

### 2. 检查是否漏记

若 `sell_orders_missing_pnl` 较大，说明部分卖单的 realized_pnl 未被 WebSocket 推送或未被正确解析。可尝试：

- 手动触发订单同步：`POST /api/orders/sync`
- 确认交易所 WebSocket 是否稳定、是否支持 realized_pnl 字段

### 3. 对比单笔订单

在订单历史页，同时查看「盈利(网格)」和「盈利(交易所)」两列，逐笔对比，可判断是整体口径差异还是个别订单异常。

---

## 小结

- **网格盈亏**：按槽位买卖配对，反映策略逻辑
- **交易所盈亏**：按持仓加权均价，反映实际结算
- **差异大甚至性质相反**：在持仓结构复杂、高位加仓后下跌时很常见
- **以交易所为准**做资金和税务处理；以网格盈亏评估策略效果
